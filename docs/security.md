# 安全模型

一个能指挥 Harness 的客户端，等价于**这台机器的完整控制权**：它可以执行 shell、
读写工作区、发起网络请求。这个前提决定了下面所有设计。

## 信任边界

```
手机 App ──(1)──▶ 公网/局域网 ──(2)──▶ 插件 ──(3)──▶ DSH 进程
```

1. **传输**：公网必须 HTTPS/WSS。插件本身不终止 TLS —— 由用户自己的反向代理
   （推荐 Cloudflare 命名隧道）负责。局域网明文 HTTP 仅作为同网段的降级选项，
   README 中明确标注风险。
2. **认证**：长期设备凭据（32 字节随机）。插件侧只存 SHA-256，不存原文；
   比对使用定时安全比较。
3. **授权**：插件不做细粒度权限——配对即全权。这与 DSH 自身的模型一致：
   桌面 Web GUI 的浏览器凭据同样是全权凭据。

## 配对

- 配对码 8 位数字，10 分钟轮换，单次使用。
- 生成入口仅限本机回环（`127.0.0.1`），不能从网络触发。
- 每台设备独立凭据，桌面端可单独吊销，吊销立即生效（下一次请求即 401）。

## 设备侧

- `deviceToken` 存 HUKS（`@ohos.security.huks`），不写普通 Preferences。
- 不在日志、崩溃上报、剪贴板中出现。
- 卸载即失效（凭据随应用数据删除，但桌面端仍应手动吊销）。

## 审批的特殊风险

审批是唯一能把“一个错误点击”变成“在宿主机上执行命令”的入口。因此：

- 手机端弹窗必须显示工具名与桌面给出的原因，不显示被截断的裸命令；
- 只支持一次性允许，没有“永远允许”，避免用户为了省事把闸门焊死；
- 手机 15 秒内未响应即让位给桌面，避免“手机没带 = 任务全卡住”；
- 桌面端始终保留最终回答权（`next()` 链路不变）。

## 不做的事

- 不做遥测、不上报会话内容、不内置任何第三方分析 SDK。
- 不代理未经 `/mobile/v1` 声明的 Host 接口；插件不是通用反向代理。
- 不支持“远程唤醒/开机”，不申请计划任务或自启动权限。
